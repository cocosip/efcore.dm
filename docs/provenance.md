## 2. Reference material

The previous implementation repository (`efcore.dm-backup`) is a **read-only reference**. It is not part of the build, no file is copied from it, and it is not a code source.

Three facts govern its use:

1. That repository's source was produced by decompiling the official `DM.Microsoft.EntityFrameworkCore` assembly and cleaning the output.
2. The official NuGet package declares **Apache-2.0** (`<license type="expression">Apache-2.0</license>`, with `requireLicenseAcceptance` set to true).
3. That source is therefore an Apache-2.0 derivative, carrying notice and change-documentation obligations. Copying whole files from it would prevent this repository from claiming MIT.

### Permitted use

| Use | Permitted |
|---|---|
| Reading it to understand Dameng dialect behaviour, such as which function maps to which SQL | Yes |
| Using it as a black-box oracle for the SQL generated by the same query | Yes |
| Deriving a list of capabilities that must be supported | Yes, because a list of facts is not an expression |
| Copying a file, or mechanically rewriting one | **No** |
| Copying comments, resource strings, or structure | **No** |

### Test for copying

A file is a copy when it is substantively isomorphic to its counterpart in the reference repository: the same private method names in the same order, the same branch structure, the same comments, or the same decompiler artifacts. Such a file is rewritten rather than cleaned.

The reason is engineering as much as licensing. The reference code carries known quality problems: `//IL_xxxx: Unknown result type` residue, `((Expression)(object)x)` casts, and wholesale copies of EF Core internal implementations. These are also defect sources, and rewriting costs less than cleaning.

### What was not carried over

The reference was inventoried type by type against this repository. Three groups of its files are deliberately absent, and a fourth is waiting on a server. Recording them here keeps a later reader from porting one of them under the impression that it is a Dameng feature.

| Group | Reference types | Why it is absent |
|---|---|---|
| SQL Server leftovers | `WrappedDmDataReader` and `DmDataReaderExtension`, `SearchConditionConvertingExpressionVisitor`, `StartsEndsWithContains`, `IOBehavior`, `EnumerableExtensions`, `MemberInfoExtensions`, `PropertyInfoExtensions`, `SharedTypeExtensions`, `StringBuilderExtensions` | Decompiled from the SQL Server provider along with the rest and never made dialect specific. Nothing calls them, and they are not Dameng behaviour to preserve |
| SQL Server full-text shape | `DmFullTextSearchFunctionsTranslator` with `FreeText` and `Contains` over an `int languageTerm` | The overloads take a Windows language identifier and translate to `CONTAINS` and `FREETEXT`, which is the SQL Server shape of both. Dameng has no counterpart verified for either, so the surface would be an API that cannot work |
| Message and guard plumbing | `DmStrings`, `DmSqlStrings`, `DmResources`, `Check` | This repository throws with the message at the call site and uses `ArgumentNullException.ThrowIfNull`, so there is no resource lookup to port |
| Store type subclasses | `DmBoolTypeMapping`, `DmByteTypeMapping`, `DmByteArrayTypeMapping`, `DmSByteTypeMapping`, `DmStringTypeMapping`, `DmDecimalTypeMapping`, `DmFloatTypeMapping`, `DmDoubleTypeMapping`, `DmDateOnlyTypeMapping`, `DmTimeOnlyTypeMapping`, `DmDateTimeTypeMapping`, `DmDateTimeOffsetTypeMapping`, `DmJsonTypeMapping` | The base mappings cover every case except the store type name and its facets, which this repository builds into the name instead of subclassing for. The row for clone semantics in the [capability matrix](capability-matrix.md) records the consequence |

Two further files are absent because their behaviour is already reached another way. The reference's `DmMigrationsAnnotationProvider` is an empty pass-through, and the differ was measured to put the value generation strategy on the old column by itself, which is what the drop of a lost identity attribute reads. The reference's `DmAnnotationCodeGenerator` and `DmCodeGenerator` are not needed, because the relational code generator leaves an annotation it does not know in the snapshot, which the row for the annotation code generator records.

A string the model gives no length is the other place the two differ: the reference names 32767 characters and switches to `clob` past that, this repository names the character large object directly, because a bounded type named without a length is not a type the server accepts in a table definition. A string that is part of a key or an index takes the same 450 and 900 the reference names, and the variable length names are its `VARCHAR2` and `NVARCHAR2`, so the two agree exactly there; the manual states that `VARCHAR2` is used the same way as `VARCHAR`. A column of the reference's shape reads back as a sized string, so a database it built is read the same way.
On a column, the reference writes a single annotation, `Dm:Identity`, holding the seed and increment as one string, and the migration files its tooling produced carry `.Annotation("Dm:Identity", "1, 1")` beside the column. This repository writes `Dm:ValueGenerationStrategy` with the seed and increment as separate annotations, and reads either form, which is what makes a migration or a snapshot written by the original provider replay against this one. The difference is only in what a newly generated file contains.
What remains unported is server dependent rather than dialect trivia: temporal tables and full-text search. A `rowversion` column is not one of them: Dameng has no column that generates a new value on every write, which the [capability matrix](capability-matrix.md) records with the measurement and the shape that works instead. Each is a row of the [capability matrix](capability-matrix.md) with the reason it waits.
## 3. EF Core

EF Core is MIT licensed and may be reused.

The strategy is to **inherit public extension points**, not to copy internal implementations:

- Allowed: deriving from `RelationalTypeMapping`, `QuerySqlGenerator`, `MigrationsSqlGenerator` and similar public base types, and calling protected virtual members.
- Allowed: reading EF Core source to understand a base type contract, and calling `base.` for the generic part.
- Avoided: copying whole EF Core internal types. Such a copy must be re-copied on every EF Core major version and is the primary source of upgrade cost.
- Exception: when copying is the only way to make something work because no extension point exists. The file header then names the source file and EF Core version, and the copy is registered in section 5.

## 4. Dameng driver

`DM.DmProvider` is a third-party ADO.NET driver supplied by Dameng. It is consumed as a NuGet dependency. Its source is not modified and not redistributed.

The driver exposes behaviour the provider has to adopt rather than invent:

| Member | Fact | Consequence |
|---|---|---|
| `DmConnection(string connectionString, bool forEFCore)` | The second parameter is the vendor's own switch for a connection driven by Entity Framework | The provider passes `true`. Leaving it off would run the provider on the path the driver keeps for other consumers |
| `DmTransaction.Save`, `Rollback(string)`, `Release` | Public overrides exist from `8.3.1.47463`; the `8.3.1.36935` line declares only the internal `do_Save`, `do_Rollback` and `do_Release` | Not the path savepoints take. The relational layer runs them as statements instead, so the driver floor is set by other members |
| `DmConnection.OpenAsync`, `CloseAsync`, `BeginTransactionAsync` | Not overridden: the asynchronous members are the `DbConnection` fallbacks | An asynchronous call is synchronous underneath. Cancellation of an in-flight statement therefore depends on the provider's own handling |
